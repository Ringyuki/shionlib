# UI

## hina-ui

- Import components from `@hina-ui/react`; the style entry is `app/app.css` (`tailwindcss`, then `@hina-ui/react/styles/tokens.css`, then `shared/ui/theme.css`).
- Zero native tags: compose components; pass `as` for semantics (`<Stack as="nav">`, `<Center as="main">`); when a component must render a button around custom layout, use `<Button asChild><Flex as="button">…</Flex></Button>`.
- hina-ui `Text` sets its own colour; inside a coloured parent (an active nav item, a solid button) add `text-inherit`.
- Layout: `Container`, `Stack`, `Inline`, `SimpleGrid`, `Grid`; text: `Heading`, `Text`; actions: `Button` (`variant`, `tone`, `size`, `icon`, `loading`), links styled as buttons with `<Button asChild><Link .../></Button>`.
- The header search trigger is a `soft` `neutral` `Button` at its natural width, with the search icon, the muted placeholder and the `/` `Kbd` in its label, as in hina-ui's CommandPalette demo.
- A custom clickable surface (the game banner) is a `Card as="button"` with `hn-interactive hn-state-layer hn-press-lg` and a `Ripple`, as hina-ui's Card docs describe; `padded={false}` when the content brings its own padding or fills the card. Never reshape a `Button` into something else, and never style hina-ui's internal markup (`[&>.hn-*]`, lint).
- A `ghost` button has padding around a box nobody sees, so on an edge its icon or text starts a few pixels inside the line everything else keeps (17 px for the default size, 11 px for `sm`), which reads as a mistake. Three ways out, by what the button is. An action that stands by itself under a label or at the end of a list (「添加线路」, 「新建收藏夹」) is `outline` `neutral`: its border sits on the edge and the padding is then inside something visible. A way back (the writing page, an opened message on a phone) is a hina-ui `Link` with an `ArrowLeft`, which has no padding at all. Actions that run on from text or close a row (like and reply under a comment, the tools above the steps box, 「删除这条线路」, the language of the intro) stay `ghost` and take `flushStart.<size>` or `flushEnd.<size>` from `~/shared/ui/flush` through `cn`: a negative margin of exactly the control's own padding (`--hn-control-px-*` plus its 1 px border), so the content meets the edge and the hover surface hangs outside it. Never a guessed `-ms-2`. Lint refuses a `ghost` button whose `className` is a plain string with `self-start`, `self-end` or `place-self-*`. A row that is itself a surface (a nav item, a list entry, the block button at the foot of a popover whose content has the same padding) is not this case.
- A page is as wide as the shell lets it be: `SiteShell` puts every page in one `Container size="xl"`, and a page adds no width of its own (no `mx-auto` with a `max-w-*`; lint `ownWidth`). Each page once chose its own cap (672, 768, 896, 920, 1136) and the user had them removed on 2026-10-11: only the upload page (`max-w-2xl`) and the profile sheet (`md:max-w-230`) keep a width, both centred. The password reset page, a two-field form reached from an email, also keeps its narrow form (`max-w-sm`); it was not among the pages the user was shown, so ask before adding a fourth. The files are listed in `ownWidthPages` in `eslint.config.js`. Widths inside a page (a text measure, a field, a dialog) are not page widths.
- What stays in view while a page scrolls is a hina-ui `Affix` (native sticky under the header, kept inside its parent); the `sticky` class is not written by hand (lint `rawSticky`; the shell's backdrop anchor is the one exception). A column beside the content is `SideColumn` (`~/shared/ui/side-column`): an `Affix` 24 px under the header (`sideOffset`) around a `ScrollArea` that from `lg` is never taller than the window, so a long list scrolls inside it instead of running off the screen, with 4 px around the content so focus rings are not cut. The section list of settings, the lists of 「我的收藏」 and the routes of a walkthrough (on its tab and on the writing page) are side columns. The account panel of the uploads page and the filters of the library are an `Affix` with the same offset around their `Card` (a `ScrollArea` would cut a card's shadow). The save bar of the writing page on a phone is `Affix position="bottom"`. In a flex row the column takes `self-start`, which `SideColumn` adds from `lg`.
- Overlays (`Popover`, `Dialog`, `Sheet`) take their trigger as children and the panel as `content`.
- Icons come from `lucide-react` (the version hina-ui uses).
- `TooltipProvider` and `Toaster` are mounted once in `root.tsx`; `UiLocaleProvider` in `lang.tsx`.
- Use tokens (`text-muted`, `border-line`, `bg-subtle`) instead of raw colours; Tailwind utilities only glue layout.

## Accent customisation

Change these only together, and recheck contrast in both themes. All other tokens are hina-ui's defaults.

### Platform colours

`app/shared/ui/platform.css` (imported after `theme.css`) holds the first of two approved additions (the other is `backdrop.css`, the frosted sheet over a page background, described with the user's page): each platform's brand colour as `--platform-<key>` and `--platform-<key>-fg`, with dark-mode values where the light ones would vanish (macOS, iOS and PSP invert to light, Linux turns dark grey), exposed to Tailwind as `bg-platform-<key>` / `text-platform-<key>-fg`. Only `PlatformTag` (`~/features/game`) uses them: a solid `Tag` in the brand colour with the platform's icon (`react-icons`). Tags that sit with it (languages, engine, game type) are neutral `variant="outline"` `Tag`s: solid neutral turns them into black blocks next to the brand colours, and soft neutral is too faint.

## Shell

- `features/shell/ui/site-shell.tsx` renders hina-ui `AppShell` with controlled sidebar state (`expanded`/`rail`, remembered in the `shionlib_sidebar` cookie) and mobile drawer state.
- The shell's `Container` is a column at least as tall as the main area: `min-h-full`, which hina-ui documents for the direct child of `AppShell`'s main area (the padding counts within it). The page content in it grows (`flex-1`), so on a short page the footer rests at the bottom of the screen; a long page pushes it down as usual. The footer's own height is never hard-coded.
- `ScrollTop` renders next to `AppShell` with `target={() => shell.current?.mainViewport}` and its default fixed position, lifted clear of the footer the way hina-ui documents it: `offset={{ y: 'var(--clear-of-footer)' }}`. The variable is set by `clearOfFooter`, which lives beside `SiteFooter` because its values follow the footer's layout (the footer's height at that width, the container's bottom padding and 8 px): 140 px, 94 px from `sm`, 56 px from `md`, 64 px from `lg`. Change them together with the footer and measure again: at the end of a long page the button must not cover a footer link at any width in any of the three languages. Nothing else in the layout moves or makes room for the button.
- The sidebar (`ui/site-sidebar.tsx`) is Shionlib's own, and like hina-ui's `Sidebar` it has no background of its own: it shares the shell's `bg-canvas` with the header and main area, separated only by its `border-e`. It contains: brand row aligned with the 56 px header, the upload action, navigation sections, and the account menu. It uses hina-ui's motion utilities (`hn-sidebar` for the width transition, `hn-sidebar-label` for fading labels), keeps every icon, the logo and the avatar centred at 34 px in both states (the rail is 69 px so its content is an even 68 px inside the 1 px border; items are 44 px wide; bordered buttons take 1 px off their start padding), swaps section titles for dividers and shows tooltips in rail, and renders a `CloseButton` inside the mobile drawer.
- A navigation that takes long shows `NavigationProgress` (`ui/navigation-progress.tsx`): a line two pixels tall in the accent colour, fixed to the top of the window above everything (`--hn-z-toast`), that takes no clicks. It is the only page-level loading indicator: a page, a tab or a list adds none of its own for a navigation, and what a list shows while it turns a page (`usePageTurn`) stays what it is. It is not hina-ui's `Progress`, and no library moves it:
  - `Progress` eases every change of its value for 300 ms and animates `width`, so a bar fed in steps lurches and stalls (the first version, with `@tanem/react-nprogress`, did: "走了一下然后就停住了"), and timers stutter exactly when a page is arriving and the main thread is busy.
  - The line is moved by CSS alone (`ui/navigation-progress.css`, the `navigation-progress` utility): one transition of `scale` to 90% over 15 s on `--hn-ease-enter-strong`, brisk at first and slowing all the way without stopping, which the browser runs off the main thread. The hook (`use-navigation-progress.ts`) only names the phase: `idle`, `loading`, `filling` (to 100% in `--hn-duration-base`), `fading` (`--hn-duration-exit`, staying full); the last two end on the element's own `transitionend`.
  - Nothing shows for a navigation that ends within 150 ms. One stretch of navigating is one run, so a second click while the first page is still loading carries on. A run that starts while the last one is still on screen goes through `idle` for a frame first, so the line restarts from the left instead of travelling backwards.
  - With reduced motion the durations are hina-ui's 1 ms tokens: the line stands at 90% while loading and is gone when the page has arrived.
- The header (`ui/site-header.tsx`) holds `SidebarTrigger`, the brand on small screens, the search form and the language menu.
- A navigation entry is `SidebarLink` (icon, label, target, `count`, `alert`) and a titled group of them is `SidebarGroup`; both are exported from `~/features/shell`, and the site's own sections use them too. A count is shown once and in one way: expanded, a solid accent `Tag` (`pill`) at the end of the row; in the rail, where the row has no end, a `Badge` on the icon. Above 99 it reads 「99+」.
- The shell can be lent to another area of the site. A layout route under the site layout exports `handle = shellAreaHandle(area)` (`~/features/shell`), where `area` is a `ShellArea<ReactNode>` (`{ title, navigation: rail => node }`), and the site layout passes `useShellArea()` to `SiteShell`: the area of the first match that carries one and whose loader has answered. The site layout never imports the feature that owns the area, so that feature's code is downloaded only with its own routes (the admin kit with hina-ui `DataTable` is 45 kB gzipped that a visitor never loads; a static import of `~/features/admin` from `routes/site.tsx` puts it into every page). With an area the sidebar shows that navigation in place of the site's sections, and the shell leaves out what belongs to the site: the upload action, the language menu and the footer. The header keeps the sidebar trigger, the search, the theme switch, and gains the messages bell with the unread count (the site's own way to the inbox is a sidebar entry the area does not have); on a phone it shows the area's title. The admin panel is the one area there is (see "Admin panel").
- The main area scrolls inside `AppShell`, which keeps its scroll position by itself once it has a `restoreKey`: top on a new page, the previous position on back, forward and reload, and the element a `#hash` names. Shionlib adds nothing to it: no hook, no inline script, no reading or writing of the position. To hina-ui every change of path or query is a new page, so a navigation that stays in view (tabs, sections and lists inside a page, a filter, an order, a query cleaned up after arriving) says so through the two tools in `~/shared/route`, which call hina-ui's `keepScrollPosition()` right before navigating: `useInPageNavigate()` returns `stay(to, { replace })` for code, and `InPageLink` is the link (`href`, and `prefetch="none"` where loading the target has an effect, as opening a message does). Both hold the position only when the navigation really changes the page in this tab: `keepScrollPosition()` stays armed until the next page change, so a click on the entry already shown, or one that opens another tab, must not call it. Nothing else imports `keepScrollPosition` or passes `preventScrollReset` (lint). A link to an element (`#resource-12`) is an ordinary link, because holding the position would keep it from reaching the element. Turning a page of a list lands at the start of that list, by the same means: the list carries `id={listStart}` (`~/shared/http/paging`) and `usePageTurn()` navigates to the page's address with that hash, so the visitor who turned the page at the bottom of the list reads on from its first entry, wherever the list sits on the page (under a game's header and tabs, under a search field), and back, forward and reload return to where each page was left. The list also takes a scroll margin, `scroll-mt-4`, which is no larger than the gap to whatever stands above it, so nothing of that (the shadow of a search field) shows at the edge; the two lists beside a panel that sticks at `xl:top-6` (the library, the uploads page) add `xl:scroll-mt-6` and start on one line with it. A `DataList` with `pagination` without the id does not pass lint; a list that is not a `DataList` (the activity feed's `Timeline`) carries the id the same way. hina-ui's `DataList` itself never scrolls the page when its page changes, and nothing scrolls by hand.

## Feedback

- Follow hina-ui's split: `Callout` is static content written into a page, `Alert` reports what just happened, `Toast` is transient. An `Alert` is always rendered and toggled with `open`, so it expands and fades instead of popping in; action failures render `<Alert tone="danger" open={message !== undefined}>` directly.
- A page whose whole state is an outcome (invalid link, search unavailable, password changed) renders `Result` or `Empty` instead of a form, not an alert.

## Sign-in

- Signing in, signing up and requesting a password reset happen in one dialog (`features/auth`, `AuthDialogProvider` in the `site` layout); the only auth page is the reset link target `/:lang/user/password/forget`. Legacy `/:lang/login` and `/:lang/register` redirect to `?auth=sign-in` / `?auth=sign-up`.
- Anything that needs an account uses `Button` from `~/shared/ui/button` with `loginRequired`, never a disabled button: a guest's click opens the dialog and is replayed on the same element once the viewer is signed in. The gate (`~/shared/ui/auth-gate`) is the only way shared code learns about the viewer.

## Theme

- Dark mode is hina-ui's `dark` class on `<html>`. The preference (`system`, `light`, `dark`) lives in the `shionlib_theme` cookie; the root loader renders `class="dark"` for an explicit dark choice and inlines `systemThemeScript()` for `system`, so the first paint is already right. `ThemeProvider`/`useTheme` (`~/shared/ui/theme-provider`) apply changes and follow the system while it is chosen; the header's `ThemeMenu` changes it.

## Brand and images

- `BrandLogo` shows `public/brand/logo.png` (from `favicon.ico`); `Wordmark` renders `app/shared/ui/wordmark-zh.svg` (「书音的图书馆」) for `zh` and `app/shared/ui/wordmark.svg` ("Shionlib") otherwise as inline SVG (`vite-plugin-svgr`, `?react`) filled with `currentColor`, so it is in the server HTML and never loads separately. `tone="brand"` (default) colours it with `text-accent` (the Shionlib blue in both themes); `tone="inherit"` follows the surrounding text, as in the footer. The Chinese wordmark has finer strokes, so each `size` renders it 20% taller (`md` 24px, `sm` 20px, `xs` 16px against 20px, 16px, 14px for the Latin one). `BrandLogo` still renders through hina-ui `Image` with `eager` and `lazy={false}`.
- API image fields are storage keys. `root.tsx` mounts hina-ui's `ImageResolverProvider` with `imageResolver(base)` (`~/shared/ui/image-resolver`), which prefixes keys with `IMAGE_BASE_URL` and passes absolute, `data:`, `blob:` and site (`/brand/...`) URLs through, for page images and `preview` alike. Give `Image` the key itself; anything that is not an `Image` (an `Avatar` `src`) resolves the key with hina-ui's `useImageResolver()`. A picture that has to be cut for its box is asked from the image processor (`IMAGE_PROCESSOR_URL`, the service whose contract is `Hikarinagi/hips` `docs/contract.md`), and only through `~/shared/ui/image-processor`: `faceImage` gives the address of a square cut on the face (`fit=cover&gravity=face`, three device pixels a pixel, `f=auto`) for a picture of the processor's own bucket (`IMAGE_BUCKET_URL`, where the catalog's pictures are, asked by object key), and nothing for any other source. Components call `useFaceImage()` (`~/shared/ui/use-face-image`), which returns `src` and `fallback` for an `Avatar` or `Image`: the cut with the picture's own address behind it, so a processor that refuses or cannot be reached shows the picture uncut (give it `imageClass="object-top"` for that case), and just the picture's own address when it cannot be processed. No other file builds a processor address. A person's picture is an `Avatar` with `name` at every size, never a round `Image`; beyond its `lg` (40px) the size is given by classes, which replace the ones `size` sets: the box (`size-16`, `size-20 sm:size-24`) and the initials from hina-ui's type scale (`text-xl` at 64px, `text-2xl` from 80px). Beside a heading that already says the name it takes `alt=""`. Click-to-enlarge is hina-ui's own `Image preview` (with `previewSize` from the API's `dims`), and images browsed together sit in one `ImageGroup`; never wrap an `Image` in a `Button` or wire a `Lightbox` by hand for this. Only images that are fully visible get `preview`: its open and close animation grows from the image's own rectangle, so an image that something overlaps (the banner under the game cover) does not use `Image preview`; it is a `Card as="button"` that opens a `Lightbox` instead. Content images keep `Image`'s default `lazy`, so they load under the skeleton and fade in; those at the top of a page (banner, cover) add `eager` for a high-priority request. `lazy={false}` drops the skeleton fade and the image's own fade-in, so it is only for small site assets that must be in the server HTML (`BrandLogo`, sign-in provider icons).
- A game's covers and screenshots carry ratings (`sexual`, `violence`), and a viewer chooses how pictures with adult content appear (settings, 「成人内容」): the API leaves them out for guests and for 「隐藏」, and the web masks them unless the viewer chose 「显示」 (`showsExplicit(viewer)`, given to the page by `ContentLimitProvider` in the site layout and read with `useShowsExplicit()`). `GamePicture` (`features/game/ui/game-picture.tsx`) is the one component that shows such a picture, and `GameCover` is the cover of a game at 3:4 in lists, rows and options; every feature uses them, and no file gives the address of a cover or a screenshot to `Image` (lint).
  - A masked picture is the picture itself, blurred: `Image` with a blur of 15% of its width on the image (`imageClass`, the frame is the `@container`; 24 px where the browser has no container units) and enlarged by half so the faded edge is cut off. The blur is the same share of the picture at every size, so a thumbnail in a list of choices and a screenshot are hidden equally. It is the one thing a cover may carry (no text, chips or gradients on covers). hina-ui's `Spoiler` is for text and is not used for pictures: Chromium does not draw its noise inside a link, and other browsers show its fallback, an empty block.
  - A picture that can be opened (`preview`: the cover of the game page, the screenshots) is shown by its mask first. The mask is a `Card as="button"` over the blurred picture with a `Tag` 「点击显示」 in its centre; a click or the Enter key replaces it with the picture, which takes the focus, and only that picture opens the preview. The mask has the box of the picture (`ratio` is required), and the picture that replaces it is already loaded, so it takes `lazy={false}` and `eager` and appears in the next frame without a skeleton. A picture that is still masked is not in its `ImageGroup`, and the banner's gallery lists only what the viewer sees without a mask (`plainPictures`), so paging through a `Lightbox` never shows it.
  - A picture that is part of a link (cards, rows, entries of a list of choices) is only blurred: the click belongs to the link, and the picture is shown on the game's page.

## Writing metadata

- Never glue facts into one string with separators (`a · b · c`, `a / b`). Facts that sit side by side are separate elements spaced by `Inline` gaps, with a small icon when the kind is not obvious (`Clock` + 「4 小时前更新」, `Download` + 「1,284 次下载」); a date reads as a phrase (「发售于 2015年12月18日」).
- A section whose content can be switched (the intro's language) keeps the switch out of the content flow: `Section aria-labelledby` with its own header row (`Heading level={2}`, the same heading `Section title` renders, and the control at the end), the control being a small ghost `Button` that opens a `DropdownMenuRadioGroup`. A `SegmentedControl` under the title reads as tabs and competes with the text.
- Catalog tags are links, so they render as `Chip asChild` around a router `Link` with a `Hash` icon (`gap-1`), never `Tag`. They link to the game library filtered by the tag's canonical name (`tagPath`, `/{lang}/game?tag=`), and show the alias when one exists. `Tag` stays for labels that do nothing (platforms, languages, file states).
- A game row (`GameRow`, search results and relations) keeps its cover at 3:4 (`w-22`), and its text fills exactly the cover's height: title and original title at the top, developer, date and resources at the bottom (`Stack justify="between"`). Never stretch or squash the cover to fit the text.
- Lists of games are hina-ui `DataList` with `GameRow` as each item (`children`), never a hand-made `Stack` plus `Pagination`. Since `GameRow` is a card, they use the grid layout: search results in columns of at least 26rem (`gridMin="26rem"`, `gridGap="md"`, so two on a desktop and one on a phone) with remote pages (`manual`, `pagination`, `total`, the page kept in the URL, `loading` while this route reloads) and `renderEmpty`; relations in columns (`gridMin="20rem"`). The list layout is for divided rows that are not cards.
- The search page (`/:lang/search`) leads with a large `SearchInput` that shows `loading` while the route reloads. Without a keyword it shows how to search (title, alias or `vid:`/`bid:`/`hid:` ids) and the trending keywords as `Chip` links. With one, the `DataList` header carries the count on the left and the 「仅显示有资源的游戏」 `Switch` on the right; an empty result explains the hidden games. The address is built by `resultsSearch` only.
- Whether a list shows games without resources is one rule everywhere a visitor can change it (the search page, the game library): the account setting is the default (guests: only games with resources), and the address overrides it for that list alone with `resources=any` or `resources=required`, the API's own `resources` parameter. `requiresResources(rule, byDefault)` gives what the switch shows and `resourceRuleFor(only, byDefault)` what to write, which is nothing when the choice equals the default (`~/features/game`); `resourceRuleFrom` reads it. The route passes the default as `filtered` (`viewer?.only_games_with_resources ?? true`). The switch never writes the account setting: that belongs to the settings page.
- The game library (`/:lang/game`, `features/library`) is the list of all games narrowed by conditions, and every condition is in the address (`?tag=&exclude=&platform=&year=&month=&sort=&order=asc&resources=&page=`, built by `librarySearch` and read by `addressFrom` only; `libraryPath` is where links lead, and a test keeps `tagPath` and `sortedGamesPath` of the game feature equal to it). The old address (`filter[tags][]=` and so on) redirects to the current one with 301 (`legacyParams`), and a page past the end to the last page. The list is a `DataList` grid of `GameTile dated="year"` (`gridMin="9rem"`, 36 a page, remote pages); its header carries the count and the order, a `Select` of named orders (`orders`: a direction is offered only where it means something, so 发售 has 最新 and 最早 and the others one each), never a second control for the direction, and there is no table view and no page-size choice. The conditions sit beside the list from `xl` in a sticky `aside` `Card` headed 「筛选」 with a link `Button` 「重置」, and below `xl` in a `Sheet` opened by a 「筛选」 button whose `Badge` counts the conditions; there the applied conditions also show above the games as removable `Chip`s (`conditionsOf`, each with the change that removes it), because the panel is out of sight. Both render the same `LibraryFilters`: tags and excluded tags are remote `MultiCombobox`es whose options show each tag's game count (loaded on opening and as the visitor types, `useTagOptions`; the API matches any of the chosen tags, and the field's description says so), platforms are `ChoiceChips` (`~/shared/ui/choice-chips`), years and months are `MultiSelect`s with an `aria-label` (months stay disabled until a year is chosen, since a month alone means nothing), and the resources `Switch`, which shows on and disabled while the order is 最近更新资源, an order that lists only games with resources. Changing a condition navigates at once (no apply button) and keeps the scroll position; a page change lands at the start of the list. While that navigation runs, the controls show the address it is going to (`useLibraryAddress` reads it from `useNavigation`), so a chip is selected the moment it is tapped and a second tap builds on the first; the list keeps the previous games under `loading`.
- A game shows as one of three cards, all from `features/game`, and none puts anything over the cover. `GameRow` is the compact row of search results and relations. `GameCard` is the horizontal card of a game whose resources changed: cover (`w-18.75`, so at 3:4 it is 100px tall, exactly the four lines beside it when all are present), title on up to two lines, original title, developers and date, then the tags the API picked for the card (at most three; soft `Tag`s with a `Hash` icon, not links, because the card already is one); below the cover and across the whole card, the newest resource (`PlatformTag`s, language `Tag`s, size) and then one line with the game's totals and 「上周更新」 at its end. The card itself is the link, so it carries no button that would only repeat the click. `GameTile` is the vertical card: the whole 3:4 cover, then the title with two lines always reserved (`min-h-[2lh]`, so tiles in a row line up), the date and first developer, and the languages that have a resource; `dated="day"` shows month and day (release lists) and `dated="year"` the year.
- The home page (`/:lang`, `features/home`) has three blocks in this order: recently updated resources (`DataList` grid of `GameCard`, `gridMin="22rem"`, the newest 12 only), this month's releases (`Carousel` of `GameTile dated="day"`, games without resources included; its arrows sit beside the heading, so the carousel takes `arrows={false}` and two `IconButton`s call `prev()` and `next()` on its ref through `useCarouselArrows`, which follows `onReady` and `onSelect` to disable them at the ends and to hide them when nothing scrolls) and hot games (`DataList` grid of `GameTile dated="year"`, `gridMin="9rem"`, in order of heat but without a printed position). Each block is loaded on its own (`Block` in `home.ts`): when one list fails, that block shows `BlockFailure` (`Empty` with a retry that revalidates the route) and the others still render. A block's heading row is `SectionHeader` (`Heading level={2}` and, at the end, a link to the full list). The home page never pages: each block shows one screenful and its link leads to the page that lists everything (recent updates: the game library sorted by them, `sortedGamesPath(locale, 'resource_updated')`; releases: `/release`; hot games: the library).
- "This month" follows the site clock, not UTC and not the visitor's: `siteMonthStart(now)` from `~/shared/i18n/site-time`, whose `siteTimeZone` is also what `IntlProvider` formats dates in. Release dates are calendar days stored at UTC midnight, so date filters are plain `YYYY-MM-DD` strings (`isoDate`).

- A document a user writes (a comment, the note of a walkthrough) is a rich text document: the JSON the API stores and describes in its contract (`RichTextDocument`, ADR 0013 in `apps/api/docs`). Three places deal with it, and each has one job.
  - `~/shared/richtext` knows the document and nothing about editing: the types (`RichDocument`, `RichNode`, `RichMark`, all derived from the contract), `blankDocument`, `plainText`, `publicText` (without spoilers, for meta), `isBlank`, `sameDocument`, and the guards `richDocument`, `documentFrom` and `linkAddressFrom` (`rich-text.schema.ts`). - Walkthroughs (`features/walkthrough`) are what a player follows through a game, not an article: an optional note and routes of steps, one walkthrough per author and game (`WalkthroughDTO`: `note`, `routes[]` with `key`, `name`, `characters`, `requires`, `condition`, `ending`, `steps[]` of kind `choice`, `save`, `load`, `note`, `gap`). ## Catalog attribution

Resource notes, file history reasons and catalog intros (VNDB descriptions) are BBCode. `parseBBCode` (`~/shared/markup/bbcode`) turns them into nodes: `b`, `i`, `u`, `s`, `quote`, `spoiler` and `mask`, and `url` with or without a value; `size` and `color` keep only their text, and unknown or unbalanced tags stay as text. A link must be an `http(s)` address or a VNDB entry path (`/c123`, resolved by `vndbUrl` from `~/shared/catalog/vndb`); anything else keeps its label as plain text. `BBCodeText` renders the nodes with hina-ui only (`Text as="strong"/"em"/"u"/"s"` carrying the surrounding tone and weight, `Link underline` opening in a new tab with `rel="noopener noreferrer nofollow ugc"`, `Blockquote`, `Spoiler`), keeps line breaks (`whitespace-pre-line`), and takes `size`, `tone` and `className` so it can stand in for the `Text` it replaces; a clamped summary adds `whitespace-normal`. Meta descriptions use `bbcodePlainText`, which drops spoiler content.

BBCode is written in `BBCodeEditor` (`~/shared/ui/bbcode-editor`), placed inside the field's `FormField` like any input: a bare `Toolbar` (`size="sm"`) with icon `ToolbarButton`s for bold, italic, strikethrough, link, quote and spoiler (no underline: notes do not need it and it reads as a link) and, at the end, a `ToolbarToggleItem` 「预览」 with an eye icon whose text is visually hidden below `sm`; the field itself is the hina `Textarea`. A tool wraps the selection in its tag, or removes the tag when the selection is already wrapped, and keeps the selection (`applyBBCodeTool`, `~/shared/markup/bbcode-edit`); a link wraps a selected address as `[url]…[/url]` and otherwise leaves the cursor at the address of `[url=]…[/url]`. Preview swaps the textarea for a `Card` with the textarea's exact box (`rounded-md`, the measured height) and text position (padding from `--hn-control-px-md` and `--hn-control-h-md`), rendering `BBCodeText`, so switching moves nothing. Never put a `SegmentedControl` or `Toggle` next to the input inside a `FormField`: they claim the field's label and error state; the toolbar's toggle group does not.

A short fixed list where several values may be chosen (resource platforms with `PlatformIcon`, languages) is a row of `Chip selectable` in a `role="group"` with an `aria-label` (`ChoiceChips`, `~/shared/ui/choice-chips`): every option is visible and one tap toggles it. Not `CheckboxGroup` (a questionnaire look) and not `MultiSelect` (hides a handful of options behind a dropdown).

Text cut with `truncate` shows its full value in a `Tooltip` only when it actually overflows: `useOverflowing()` (`~/shared/ui/use-overflowing`, a `ResizeObserver`) gives the ref and the flag, the `Tooltip` is `disabled={!overflowing}` and the trigger gets `tabIndex={0}` only then. The trigger is sized to its text (`w-fit` with a `max-w-*`), otherwise the tooltip centres on an empty full-width box.

Game, character and developer data comes from Hikarinagi's open API, whose terms require naming Hikarinagi as the source and linking to the entry. Every page that shows such an entry renders `CatalogAttribution` (`~/shared/ui/catalog-attribution`) with the entity and its `h_id`: the text 「条目数据来自」 followed by Hikarinagi's wordmark (`app/shared/ui/hikarinagi-wordmark.svg`, inline, colours untouched) linking to `HIKARINAGI_SITE_URL/<galgames|producers|characters>/<id>`. Entry and editor URLs come from `~/shared/catalog/hikarinagi`. The tab that shows the catalog data (the game's info tab) ends with `CatalogCorrection` (「资料有误或不全？去 Hikarinagi 编辑」), linking to the entry's editor; corrections are not offered from menus. The Hikarinagi ID button keeps using `public/brand/hikarinagi-icon.webp`.

## Messages and locales

- Locales: `zh` (default), `en`, `ja`; URLs are `/<locale>/...`; `/` redirects by the `shionlib_locale` cookie, then `Accept-Language`, then `zh`.
- Each feature owns `messages/{zh,en,ja}.json`, registered under the feature name in `app/messages/{zh,en,ja}.ts`. `zh` defines the `Messages` type; `en` and `ja` must match it.
- Messages use ICU syntax (`{count, plural, ...}`, `{date, date, long}`) and are read with `useTranslations('<feature>')`; keys are checked at compile time.
- Dates are formatted in `Asia/Shanghai` on both server and client so hydration matches.
- Text from the API (titles, `failure.message`) is already localized or multilingual; pick game titles with `gameTitle(game, locale)`.
- The admin panel is written in Chinese only, so its texts are not part of the three per-locale message objects and are not sent to visitors. Each admin feature keeps `messages/zh.json` alone; `app/messages/admin/zh.ts` assembles them (`adminMessages`), the admin layout's loader delivers them (`loadAdminMessages`), and `AdminMessages` (`~/features/admin`) merges them onto the site's messages through `ExtraMessages` (`~/shared/i18n/extra-messages`) in the two places admin texts are read: around the admin's pages (`routes/admin.tsx`) and around what the admin lends to the shell (`adminArea`). `use-intl.d.ts` types `Messages` as the site's plus the admin's, so the keys are checked like any other.

## Docs

- The docs (`/:lang/docs` and `/:lang/docs/:category/:name`, `features/docs`) render documents that are written and kept in the repository: one MDX file per document and language under `content/<locale>/<category>/`, with a head (frontmatter: `title`, `description`, `banner`, `date`, `author_uid`, `author_name`, `author_avatar`). The documents are content, not interface text: the pages show them as they are written, and a change to what a document says is a change to its file. Their addresses are the ones the documents have always had, so links from elsewhere keep working; a document that is taken down leaves its address in `retired` (`docs.ts`), and `docLoader` answers it with a permanent redirect to the list of documents.
- The server knows every document from its head alone (`docs.server.ts` reads the heads eagerly, validates them with `docFrom` and fails the build on a document without a place or a valid head). A category is a folder: `guides`, `about`, `dev`, in that order. Inside a category the documents are read in the order they give themselves: `order` in the head, the smaller first; a document without one comes after those that have it, the newest first (`inOrder`). That one order is the list and the previous and next links, which run on across categories. Titles come from the documents, so adding one needs no message and no list to edit; only category names are messages (`docs.category.*`).
- `/:lang/docs` (`DocsPage`, the sixth PRD prototype, canvas 4SRydNX4…) is the list: one section per category, and in it one row per document (`DocRow`): the cover at 16:9 (152 px wide, 112 px on a phone), the title and the summary cut at two lines. The whole row is the link (`entryLink`). Two columns once the container is 896 px wide (`@4xl`), one below. No author and no date there; the document's page shows them. Section headings are `Heading level={2} size="lg"` in a `Stack as="section"`, since `Section` fixes its heading at a size the prototype does not use.
- A document's page (`DocPage`) is for reading, so it has no column that lists every document: a link back to the list (the idiom of the resource page), then the head and the body on the same two columns (`docColumns`): the text at most 760 px wide and a rail of 280 px, 40 px apart, left-aligned like every page (a text measure, not a page width, so no `mx-auto`). The head (`DocHead`) is `PageHeader` (title, summary, and under it the author with a link to the profile and the date) with the cover at 16:9 in the rail's column, eager and not lazy since it is above the fold. The body (`DocView`) is the document in `Prose`, then a `Divider`, the link to its source on GitHub (`sourceUrl`) and `PrevNext` labelled 「上一篇」 and 「下一篇」; beside it the rail (`ContentsRail`: a small heading 「本页目录」 and hina-ui `Anchor` in a `SideColumn`, the second and third heading levels). Below a container of 896 px the rail is gone: the cover stays beside the title (240 px), and the table of contents becomes `ContentsFold`, a `Card` holding a `Collapsible` in front of the body, closed until asked for. Below 576 px the cover moves above the title at full width.
- The body is loaded on demand, one chunk per document and language: `readPage(locale, doc)` (`docs-content.ts`) keeps the promise of each page and `DocView` reads it with `use`. No `Suspense` boundary wraps it: the server waits for the page, so the document is in the first HTML, and a navigation keeps the previous page until the next document has arrived. Never wrap it in a boundary with a fallback, and never import a document statically into a page.
- What a document may contain is `docParts` (`ui/doc-parts.tsx`): links (an address starting with `/` is a page of this site and keeps the language it names or gets the reader's, `#…` is a heading of the same document, anything else opens in a new tab), images as hina-ui `Image` with `preview`, a one-pixel border and rounded corners (screenshots stay light in dark mode, the border sets them off), fenced code as `CodeBlock` with its language, tables as hina-ui `Table` (`secondary`, no hover) so a wide table scrolls by itself, and `<Ellipsis />`, the mark of the more-actions menu the documents refer to. Everything else is plain Markdown that `Prose` styles. A component that is not prose (cards, grids) does not belong in a document, because `Prose` restyles every tag inside it. Pictures a document shows live in `public/assets/images/<name>/`, screenshots of the site once per language under `<name>/<locale>/`. A picture never moves the page when it loads: `mdx/pictures.ts` (a rehype plugin beside `sections`) measures every picture's file at build time and writes the size it is shown at onto it (a name ending in `@2x` is shown at half its pixels), and `DocImage` hands hina-ui `Image` that `ratio` and caps the frame at that width, so a small picture is not blown up to the column either. A picture that is not a file under `public/` (a missing file, an address on another site) fails the build, since its size cannot be known.
- `mdx/sections.ts` (a rehype plugin in the Vite and test configuration) gives every heading the anchor it has always had, made from its text (`anchorOf`: lower case, spaces to hyphens, punctuation dropped; a repeated one gets `-1`, `-2`), and exports the second and third levels as `sections` for the table of contents. It asks nothing of a document and never fails on one.
- Friend sites have a page of their own, `/:lang/friend-link` (`features/friends`): a grid of cards (logo as `Avatar`, name, host, the site's own description), each card a link that opens the site in a new tab. The list is data in `friends.ts`. The footer links to it; the sidebar's 「文档」 links to the docs.

## Admin panel

- The admin panel (`/zh/admin/**`, the seventh PRD prototype, artifact 8idWEq5U…) is part of the web client, not an app of its own. Its routes sit inside the `routes/pages.tsx` layout under `routes/admin.tsx`, so the site layout (viewer, running uploads, unread messages) stays mounted and the shell is the site's shell with the admin's navigation (`area`, see "Shell"). It is Chinese only: `adminLoader` redirects an admin address under another language to `/zh/admin/...` (`adminAddress`), and `admin/*` without a language (the links in mails and older notices) goes through `routes/locale-redirect.ts`.
- Who may enter is decided by the API alone. The layout's loader asks for `GET /admin/pending`; a 401 or 403 becomes the ordinary error page inside the site shell, with the site's own sidebar, because the shell takes an area only from a match whose loader has answered. The web client never compares roles to guard a page. `isStaff(viewer)` only decides whether the account menu offers 「管理后台」, and `isSuperAdmin(viewer)` whether an action only a super administrator may take is enabled; such an action stays visible and says why it is disabled.
- Slices: `features/admin` is the area itself (addresses in `adminPaths`, the navigation, the overview, and the kit below); every section is a slice of its own named `admin-<thing>` (`admin-report`, `admin-check`), with the message namespace `admin<Thing>`. A section's navigation entry is added to `navigationOf` when its page lands, never before. The counts beside the entries come from the same `GET /admin/pending` (`usePending()`), which every command revalidates.
- A list is a table in a card (`Panel` when it has a title, `Card padded={false}` with a toolbar row when the filters are its head), built with `RecordTable` (`~/features/admin`): hina-ui `DataTable` in its `secondary` form, the first and last cells aligned with the card's padding (`--hn-panel-p`), 20 rows a page, `Pagination` in the foot through `usePageTurn`. Columns are `RecordColumn`s: `fill` for the one that takes the remaining width, `wide` for those that only show from `md` up, `className` for a width of its own. No column has a fixed pixel width, since hidden columns of a fixed-layout table keep their width and squeeze the rest. On a phone the header row is gone and only the main column and the status column remain; what the hidden columns said goes into the main cell's third line (`TwoLines narrow`). Everything a list is narrowed by lives in the address (`?status=`, `?reason=`, `?result=`, `?page=`), read by a `filterFrom` in the slice's `*.schema.ts`, written with `searchSet`, navigated with `useInPageNavigate`.
- A row opens its item beside the list: `ReviewPane` is hina-ui `Drawer` (576 px) from `md` up and `Sheet` on a phone. Which item is open is in the address too (`?id=` for a report, `?case=` for a file check), so a notice can link straight to it and Back closes it. The loader that lists also loads the opened item with everything its pane shows; an id that no longer exists is dropped from the address. The pane keeps showing the last item while it closes (`useLast`), and whether it is a form or a record is fixed when it opens (`useOpenState`), since the item changes under it the moment the review is saved. Its sections are `PaneSection`s; facts are horizontal `DescriptionList`s with `[--hn-dl-term-width:5rem]`.
- A review form follows the dialog rules: the `Form` in the content, the buttons in the footer, `useFormErrors` for what the API refuses. Nothing is chosen for the administrator: the verdict starts empty and the schema asks for it (`issue('verdict')`). The form says what the choice will do before it is made, with the numbers the API gives (`/admin/content/download-resource-report-policy`, `/admin/content/malware-scan-policy`), never with numbers written into a text. Text that depends on the choice is an `Alert` shown with `open`. An action taken from a row (放行, 删除, 重新检查, 移除) asks first in one `AlertDialog` per table, kept mounted, whose `onConfirm` awaits the command's `confirm`.
- The overview's chart is ECharts, the one chart library, loaded only there: `use-line-chart.ts` imports `echarts/core` and the parts it uses on demand and creates the instance only for the mount that is still alive (Strict Mode mounts twice). Its colours are read from hina-ui's tokens on the host element and it redraws when the theme changes. `lineOption` (`admin-chart.ts`) is pure: two lines of different magnitude get an axis each, both with four intervals of a round whole step (`axisStep`), so the grid lines serve both.

- Downloading (`~/features/download`): `DownloadButton resourceId file` is a `SplitButton`. The button uses the visitor's default method; the menu lists the browser, aria2 and the game managers that are shown (each with its logo; ReinaManager and PotatoVN are disabled with the reason when the game has no Bangumi id, and a default that cannot be used for a game falls back to the browser), then 「复制下载链接」, then 「下载设置」. - A page split into tabs (the game page: `/:lang/game/:id`, `/info`, `/characters`) is a parent route with one child route per tab. The parent loader loads everything the tabs share, so switching tabs never reloads the header; child routes have no loader of their own when the parent already holds their data and read it from the typed `matches` prop (`const [, , site, , game] = matches`: root, lang, site, pages, game). The tab strip is hina-ui `Tabs` with `value` taken from the URL and `onValueChange` navigating through `useInPageNavigate()` (`~/shared/route/use-in-page-navigate`), so the page stays where it is (see the shell's scroll position above).
- Slow, optional data (external ratings) is returned from the loader as an unawaited promise that never rejects at all: the use-case settles every request (`Promise.allSettled`) and drops what failed, because a promise that rejects before React Router attaches to it is an unhandled rejection that takes the server process down. It renders through `<Suspense>`/`<Await>`, and the fallback must take exactly the space of the result (no layout shift): render the same slots the result will fill, known from the synchronous data (which sources a game is linked to), with values that occupy the same line (a dash) and `Skeleton` wrapping the lines that will appear. Every reload of the page data (after any command on the page) brings a new pending promise; handed to `<Await>` it would suspend again, and since React Router updates inside a transition, React would hold back the whole update, the posted comment included, until the slow request answers. So the component keeps the promise it first got (`useState(promise)`, with `key` set to what the data belongs to, the game id) and reloads never make the page wait: measured with a cold score cache, a posted comment appears after about 0.3 s whether the scores take 0.4 s or 5 s.
