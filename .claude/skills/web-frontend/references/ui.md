# UI

## hina-ui

- Import components from `@hina-ui/react`; the style entry is `app/app.css` (`tailwindcss`, then `@hina-ui/react/styles/tokens.css`, then `shared/ui/theme.css`).
- Zero native tags: compose components; pass `as` for semantics (`<Stack as="nav">`, `<Center as="main">`); when a component must render a button around custom layout, use `<Button asChild><Flex as="button">…</Flex></Button>`.
- hina-ui `Text` sets its own colour; inside a coloured parent (an active nav item, a solid button) add `text-inherit`.
- Layout: `Container`, `Stack`, `Inline`, `SimpleGrid`, `Grid`; text: `Heading`, `Text`; actions: `Button` (`variant`, `tone`, `size`, `icon`, `loading`), links styled as buttons with `<Button asChild><Link .../></Button>`.
- The header search trigger is a `soft` `neutral` `Button` at its natural width, with the search icon, the muted placeholder and the `/` `Kbd` in its label, as in hina-ui's CommandPalette demo.
- A custom clickable surface (the game banner) is a `Card as="button"` with `hn-interactive hn-state-layer hn-press-lg` and a `Ripple`, as hina-ui's Card docs describe; `padded={false}` when the content brings its own padding or fills the card. Never reshape a `Button` into something else, and never style hina-ui's internal markup (`[&>.hn-*]`, lint).
- Overlays (`Popover`, `Dialog`, `Sheet`) take their trigger as children and the panel as `content`.
- Icons come from `lucide-react` (the version hina-ui uses).
- `TooltipProvider` and `Toaster` are mounted once in `root.tsx`; `UiLocaleProvider` in `lang.tsx`.
- Use tokens (`text-muted`, `border-line`, `bg-subtle`) instead of raw colours; Tailwind utilities only glue layout.

## Accent customisation

`app/shared/ui/theme.css` follows hina-ui's "自定义主题" guide and nothing more: it sets the six accent roles for `:root` and `.dark`.

| Role                 | Light                                                            | Dark                     |
| -------------------- | ---------------------------------------------------------------- | ------------------------ |
| `--hn-accent`        | `#34a2d5` (Shionlib blue)                                        | `#34a2d5`                |
| `--hn-accent-on`     | `#ffffff` (blue with white text is the Shionlib brand; required) | `#ffffff`                |
| `--hn-accent-text`   | `#206a8e` (6.0:1 on surface, 5.3:1 on soft)                      | `#4cb8ea`                |
| `--hn-accent-soft`   | accent 12 % over surface                                         | accent 24 % over surface |
| `--hn-accent-border` | accent 34 %                                                      | accent 30 %              |
| `--hn-focus-ring`    | `#2784b0`                                                        | `#4cb8ea`                |

Change these only together, and recheck contrast in both themes. All other tokens are hina-ui's defaults.

### Platform colours

`app/shared/ui/platform.css` (imported after `theme.css`) holds the one approved addition: each platform's brand colour as `--platform-<key>` and `--platform-<key>-fg`, with dark-mode values where the light ones would vanish (macOS, iOS and PSP invert to light, Linux turns dark grey), exposed to Tailwind as `bg-platform-<key>` / `text-platform-<key>-fg`. Only `PlatformTag` (`~/features/game`) uses them: a solid `Tag` in the brand colour with the platform's icon (`react-icons`). Tags that sit with it (languages, engine, game type) are neutral `variant="outline"` `Tag`s: solid neutral turns them into black blocks next to the brand colours, and soft neutral is too faint.

## Shell

- `features/shell/ui/site-shell.tsx` renders hina-ui `AppShell` with controlled sidebar state (`expanded`/`rail`, remembered in the `shionlib_sidebar` cookie) and mobile drawer state.
- The shell's `Container` is a column at least as tall as the main area, `min-h-[calc(100vh-3.5rem-1px)]` (`AppShell` is `h-screen` and its header is `h-14` plus a 1px border; the padding counts within it). The page content in it grows (`flex-1`), so on a short page the footer rests at the bottom of the screen; a long page pushes it down as usual. The footer's own height is never hard-coded.
- `ScrollTop` keeps hina-ui's defaults: it renders next to `AppShell` with `target={() => shell.current?.mainViewport}` and its default fixed position. Nothing in the layout moves or makes room for it; where it covers content, hina-ui fixes that upstream.
- The sidebar (`ui/site-sidebar.tsx`) is Shionlib's own, and like hina-ui's `Sidebar` it has no background of its own: it shares the shell's `bg-canvas` with the header and main area, separated only by its `border-e`. It contains: brand row aligned with the 56 px header, the upload action, navigation sections, and the account menu. It uses hina-ui's motion utilities (`hn-sidebar` for the width transition, `hn-sidebar-label` for fading labels), keeps every icon, the logo and the avatar centred at 34 px in both states (the rail is 69 px so its content is an even 68 px inside the 1 px border; items are 44 px wide; bordered buttons take 1 px off their start padding), swaps section titles for dividers and shows tooltips in rail, and renders a `CloseButton` inside the mobile drawer.
- The header (`ui/site-header.tsx`) holds `SidebarTrigger`, the brand on small screens, the search form and the language menu.
- The main area scrolls inside `AppShell`; `useMainScrollRestore` wires hina-ui's scroll restorer to React Router (top on new pages, previous position on back/forward and reload), and `root.tsx` injects `firstPaintRestoreScript()`.

## Feedback

- Follow hina-ui's split: `Callout` is static content written into a page, `Alert` reports what just happened, `Toast` is transient. An `Alert` is always rendered and toggled with `open`, so it expands and fades instead of popping in; action failures render `<Alert tone="danger" open={message !== undefined}>` directly.
- A page whose whole state is an outcome (invalid link, search unavailable, password changed) renders `Result` or `Empty` instead of a form, not an alert.

## Sign-in

- Signing in, signing up and requesting a password reset happen in one dialog (`features/auth`, `AuthDialogProvider` in the `site` layout); the only auth page is the reset link target `/:lang/user/password/forget`. Legacy `/:lang/login` and `/:lang/register` redirect to `?auth=sign-in` / `?auth=sign-up`.
- Anything that needs an account uses `Button` from `~/shared/ui/button` with `loginRequired`, never a disabled button: a guest's click opens the dialog and is replayed on the same element once the viewer is signed in. The gate (`~/shared/ui/auth-gate`) is the only way shared code learns about the viewer.

## Theme

- Dark mode is hina-ui's `dark` class on `<html>`. The preference (`system`, `light`, `dark`) lives in the `shionlib_theme` cookie; the root loader renders `class="dark"` for an explicit dark choice and inlines `systemThemeScript()` for `system`, so the first paint is already right. `ThemeProvider`/`useTheme` (`~/shared/ui/theme-provider`) apply changes and follow the system while it is chosen; the header's `ThemeMenu` changes it.

## Brand and images

- `BrandLogo` shows `public/brand/logo.png` (from `favicon.ico`); `Wordmark` renders `app/shared/ui/wordmark-zh.svg` (「书音的图书馆」) for `zh` and `app/shared/ui/wordmark.svg` ("Shionlib") otherwise as inline SVG (`vite-plugin-svgr`, `?react`) filled with `currentColor`, so it is in the server HTML and never loads separately. `tone="brand"` (default) colours it with `text-accent` (the Shionlib blue in both themes); `tone="inherit"` follows the surrounding text, as in the footer. The Chinese wordmark has finer strokes, so each `size` renders it 20% taller (`md` 24px, `sm` 20px, `xs` 16px against 20px, 16px, 14px for the Latin one). `BrandLogo` still renders through hina-ui `Image` with `eager` and `lazy={false}`.
- API image fields are storage keys. `root.tsx` mounts hina-ui's `ImageResolverProvider` with `imageResolver(base)` (`~/shared/ui/image-resolver`), which prefixes keys with `IMAGE_BASE_URL` and passes absolute, `data:`, `blob:` and site (`/brand/...`) URLs through, for page images and `preview` alike. Give `Image` the key itself; anything that is not an `Image` (an `Avatar` `src`) resolves the key with hina-ui's `useImageResolver()`. Click-to-enlarge is hina-ui's own `Image preview` (with `previewSize` from the API's `dims`), and images browsed together sit in one `ImageGroup`; never wrap an `Image` in a `Button` or wire a `Lightbox` by hand for this. Only images that are fully visible get `preview`: its open and close animation grows from the image's own rectangle, so an image that something overlaps (the banner under the game cover) does not use `Image preview`; it is a `Card as="button"` that opens a `Lightbox` instead. Content images keep `Image`'s default `lazy`, so they load under the skeleton and fade in; those at the top of a page (banner, cover) add `eager` for a high-priority request. `lazy={false}` drops the skeleton fade and the image's own fade-in, so it is only for small site assets that must be in the server HTML (`BrandLogo`, sign-in provider icons).

## Writing metadata

- Never glue facts into one string with separators (`a · b · c`, `a / b`). Facts that sit side by side are separate elements spaced by `Inline` gaps, with a small icon when the kind is not obvious (`Clock` + 「4 小时前更新」, `Download` + 「1,284 次下载」); a date reads as a phrase (「发售于 2015年12月18日」).
- A section whose content can be switched (the intro's language) keeps the switch out of the content flow: `Section aria-labelledby` with its own header row (`Heading level={2}`, the same heading `Section title` renders, and the control at the end), the control being a small ghost `Button` that opens a `DropdownMenuRadioGroup`. A `SegmentedControl` under the title reads as tabs and competes with the text.
- Catalog tags are links, so they render as `Chip asChild` around a router `Link` with a `Hash` icon (`gap-1`), never `Tag`. They link to the game library filtered by the tag's canonical name (`tagPath`, `/{lang}/game?tag=`), and show the alias when one exists. `Tag` stays for labels that do nothing (platforms, languages, file states).
- A game row (`GameRow`, search results and relations) keeps its cover at 3:4 (`w-22`), and its text fills exactly the cover's height: title and original title at the top, developer, date and resources at the bottom (`Stack justify="between"`). Never stretch or squash the cover to fit the text.
- Lists of games are hina-ui `DataList` with `GameRow` as each item (`children`), never a hand-made `Stack` plus `Pagination`. Since `GameRow` is a card, they use the grid layout: search results in columns of at least 26rem (`gridMin="26rem"`, `gridGap="md"`, so two on a desktop and one on a phone) with remote pages (`manual`, `pagination`, `total`, the page kept in the URL, `loading` while this route reloads) and `renderEmpty`; relations in columns (`gridMin="20rem"`). The list layout is for divided rows that are not cards.
- The search page (`/:lang/search`) leads with a large `SearchInput` that shows `loading` while the route reloads. Without a keyword it shows how to search (title, alias or `vid:`/`bid:`/`hid:` ids) and the trending keywords as `Chip` links. With one, the `DataList` header carries the count on the left and the 「仅显示有资源的游戏」 `Switch` on the right; an empty result explains the hidden games. The address is built by `resultsSearch` only.
- Whether a list shows games without resources is one rule everywhere a visitor can change it (the search page, the game library): the account setting is the default (guests: only games with resources), and the address overrides it for that list alone with `resources=any` or `resources=required`, the API's own `resources` parameter. `requiresResources(rule, byDefault)` gives what the switch shows and `resourceRuleFor(only, byDefault)` what to write, which is nothing when the choice equals the default (`~/features/game`); `resourceRuleFrom` reads it. The route passes the default as `filtered` (`viewer?.only_games_with_resources ?? true`). The switch never writes the account setting: that belongs to the settings page.
- The game library (`/:lang/game`, `features/library`) is the list of all games narrowed by conditions, and every condition is in the address (`?tag=&exclude=&platform=&year=&month=&sort=&order=asc&resources=&page=`, built by `librarySearch` and read by `addressFrom` only; `libraryPath` is where links lead, and a test keeps `tagPath` and `sortedGamesPath` of the game feature equal to it). The old address (`filter[tags][]=` and so on) redirects to the current one with 301 (`legacyParams`), and a page past the end to the last page. The list is a `DataList` grid of `GameTile dated="year"` (`gridMin="9rem"`, 36 a page, remote pages); its header carries the count and the order, a `Select` of named orders (`orders`: a direction is offered only where it means something, so 发售 has 最新 and 最早 and the others one each), never a second control for the direction, and there is no table view and no page-size choice. The conditions sit beside the list from `xl` in a sticky `aside` `Card` headed 「筛选」 with a link `Button` 「重置」, and below `xl` in a `Sheet` opened by a 「筛选」 button whose `Badge` counts the conditions; there the applied conditions also show above the games as removable `Chip`s (`conditionsOf`, each with the change that removes it), because the panel is out of sight. Both render the same `LibraryFilters`: tags and excluded tags are remote `MultiCombobox`es whose options show each tag's game count (loaded on opening and as the visitor types, `useTagOptions`; the API matches any of the chosen tags, and the field's description says so), platforms are `ChoiceChips` (`~/shared/ui/choice-chips`), years and months are `MultiSelect`s with an `aria-label` (months stay disabled until a year is chosen, since a month alone means nothing), and the resources `Switch`, which shows on and disabled while the order is 最近更新资源, an order that lists only games with resources. Changing a condition navigates at once (no apply button) and keeps the scroll position; a page change scrolls to the top. While that navigation runs, the controls show the address it is going to (`useLibraryAddress` reads it from `useNavigation`), so a chip is selected the moment it is tapped and a second tap builds on the first; the list keeps the previous games under `loading`.
- A game shows as one of three cards, all from `features/game`, and none puts anything over the cover. `GameRow` is the compact row of search results and relations. `GameCard` is the horizontal card of a game whose resources changed: cover (`w-18.75`, so at 3:4 it is 100px tall, exactly the four lines beside it when all are present), title on up to two lines, original title, developers and date, then the tags the API picked for the card (at most three; soft `Tag`s with a `Hash` icon, not links, because the card already is one); below the cover and across the whole card, the newest resource (`PlatformTag`s, language `Tag`s, size) and then one line with the game's totals and 「上周更新」 at its end. The card itself is the link, so it carries no button that would only repeat the click. `GameTile` is the vertical card: the whole 3:4 cover, then the title with two lines always reserved (`min-h-[2lh]`, so tiles in a row line up), the date and first developer, and the languages that have a resource; `dated="day"` shows month and day (release lists) and `dated="year"` the year.
- The home page (`/:lang`, `features/home`) has three blocks in this order: recently updated resources (`DataList` grid of `GameCard`, `gridMin="22rem"`, the newest 12 only), this month's releases (`Carousel` of `GameTile dated="day"`, games without resources included; its arrows sit beside the heading, so the carousel takes `arrows={false}` and two `IconButton`s call `prev()` and `next()` on its ref through `useCarouselArrows`, which follows `onReady` and `onSelect` to disable them at the ends and to hide them when nothing scrolls) and hot games (`DataList` grid of `GameTile dated="year"`, `gridMin="9rem"`, in order of heat but without a printed position). Each block is loaded on its own (`Block` in `home.ts`): when one list fails, that block shows `BlockFailure` (`Empty` with a retry that revalidates the route) and the others still render. A block's heading row is `SectionHeader` (`Heading level={2}` and, at the end, a link to the full list). The home page never pages: each block shows one screenful and its link leads to the page that lists everything (recent updates: the game library sorted by them, `sortedGamesPath(locale, 'resource_updated')`; releases: `/release`; hot games: the library).
- "This month" follows the site clock, not UTC and not the visitor's: `siteMonthStart(now)` from `~/shared/i18n/site-time`, whose `siteTimeZone` is also what `IntlProvider` formats dates in. Release dates are calendar days stored at UTC midnight, so date filters are plain `YYYY-MM-DD` strings (`isoDate`).
- A user's page (`/:lang/user/:id`, `features/profile`) answers what that person uploaded and what they keep. Its header is the picture (a round `Image` of 96px with the `empty` slot showing a user icon, since `Avatar` stops at 40px), the name with the marks the API gives as booleans (`is_sponsor`, `is_admin`, `is_banned`; never read `role` or `status` numbers), the bio as plain text and the date the account was made; a cover, when the user has one, is a banner the picture overlaps as on the game page; the owner gets 「编辑资料」. Counts are printed once, on the tabs. The tabs are child routes like the game page's (`useProfileTabs`): 上传 at the profile's own address and 收藏夹 at `/favorites/:listId?`; the tabs for comments and walkthroughs arrive with those features. 上传 is a `DataList` grid of `UploadCard` (`gridMin="22rem"`, remote pages): the game's cover and title, `PlatformTag`s and language `Tag`s, the first file's name with 「等 N 个文件」, downloads and the update time; the card links to the resource on its game page (`uploadPath`). The old `/uploads` and `/edits` addresses redirect to the profile.
- The favorites tab (`features/favorite`, `FavoritesView`) is where lists are kept in order; games are added from the game page's bookmark button. Beside the games sits the list of lists: hina `NavLink`s in a `nav` from `lg` (name, a lock when private, the number of games) and a `Select` below it, with 「新建收藏夹」 under them for the owner. A `NavLink` takes the router through `as`, which needs a link component that accepts `href`: `InPageLink` from `~/features/shell` (a router `Link` that keeps the scroll position), never `asChild`, which in hina-ui 1.7.6 puts the link inside the label instead of making it the row. The games are a `DataList` in its list layout with its own anatomy, because here entries are managed, not browsed: cover (`mediaRatio={3 / 4}`), the title as a link, the note, the developers and 「加入于 …」, and for the owner one `⋯` menu (编辑备注, 移出收藏夹). The list's heading (name, 私密 `Tag`, count, description) is the `DataList` header with the owner's `⋯` (编辑收藏夹, 删除收藏夹; the default list cannot be deleted, and its name is `listLabel`'s 「默认收藏夹」 so its edit dialog has no name field). Notes are edited in a `Dialog` with a `Textarea`, not in place: they may run to 2,000 characters. Taking a game out happens at once and its toast offers 「撤销」, which puts the game back with its note; while that runs the list shows `loading`. Deleting a list asks first (`AlertDialog`), does not revalidate and navigates to the lists, since the address it was on no longer exists. A list that is not among those the viewer may see is a 404.
- Settings (`/:lang/user/settings/:section`) is a parent route with one child route per section (`personal`, `security`, `connections`, `download`, `site`; the bare address redirects to the first), the legacy addresses unchanged. `features/settings` owns the page (`SettingsPage`: the title, the section list as `NavLink`s from `lg` and as a `Select` below it, a sign-in `Result` for guests) and the sections about the person and the browser (profile, downloads, site); `features/account` owns the two about credentials (`SecuritySection`, `ConnectionsSection`) with their loaders, which answer `null` for a guest instead of failing. The page is one block centred in the main area (`mx-auto w-full max-w-4xl` around the title, the section list and the panels), like every page that is narrower than the main area (upload, walkthrough editor): never a narrow column left against one side. A section is a column of hina-ui `Panel`s, one per thing that is saved on its own: there is no page-wide save. A panel's `title` and `description` say what it is, its `actions` hold the one button that opens a dialog (修改, 添加, 关联), and a panel without a control in its body puts its explanation there as muted text, because a `Panel` with an empty body loses its bottom padding. A single-field panel does not repeat its title as the field's label (the input takes `aria-label`).
  - A choice saves the moment it is made and shows the value being saved until the reload brings the stored one: `usePreferences()` from `~/features/viewer` (language, adult content, only games with resources; one hook call per control so they do not share a request), whose options come from the API contract (`contentLimits`, `languages` from the generated constraints). Options that need a sentence each are a `RadioGroup` with descriptions; the theme is a `SegmentedControl`; an on/off is a `Switch` with a `description`.
  - The language is changed in one way everywhere (`useLanguage()` from `~/features/viewer`, used by the header menu and by settings): it writes the `shionlib_locale` cookie that `/` follows, saves the language to the account when signed in, and navigates to the same page in that language.
  - Text is saved with a 「保存」 button at the end of its form, disabled until something changed. The user name is checked while it is typed (`useRename`: debounced, quiet, the verdict shown under the field and a taken name set as the field's error).
  - What stays in the browser says so in its panel (theme, download method, aria2). Download settings are written with `storeDownloadSettings` and read with `useDownloadSettings` (`~/features/download`); the aria2 form remounts by `key` when the stored value arrives after hydration. 「测试连接」 calls `reachAria2` (`~/shared/vendor/aria2`) and shows the answer in an `Alert` kept mounted in the form.
  - Changing the email asks for a code at the current address and one at the new address in the same dialog; the ids of the codes that were sent live in `useOpenState`, so reopening the dialog starts over, while the resend countdown (`useCodeCooldown` from `~/features/auth`) keeps running. A passkey is added in a dialog that asks only for a name and then lets the browser take over (`usePasskeyRegistration`); passkeys are a `DataList` whose rows end in a delete button that asks first. Returning from Hikarinagi ID, the connections loader reads `oidc_linked` / `oidc_error` from the address and the section reports it once as a toast with the reason code, then removes the parameters.
- Messages (`/:lang/message/:category?`, `features/message`; the categories keep the old paths `system`, `comment-reply`, `comment-like`) read like a mailbox: the list on the left, the opened message on the right, and on a phone one or the other with a 「返回消息列表」 link. The API writes every message in the language of the page, so the client shows `title`, `excerpt`, `content` and `link_text` as they come and never touches `meta`. The opened message is in the address (`?m=`), and the loader opens it before it lists, because opening marks it read. The header says how many are unread and holds 「全部标为已读」; the categories are a `SegmentedControl` over the paths; a row is a link with an unread `Indicator`, the title, the time and two lines of excerpt, and the opened row carries `aria-current`. The message shows its kind as a `Tag`, the sender when there is one, the text, the game it is about as a `GameRow`, and its link (a `Button` inside the site, with the page's language prefixed by `linkTarget`; a plain `Link` in a new tab outside it). The original comment of a reply or like arrives with the comments feature.
  - The unread count is live. `routes/site.tsx` loads it and wraps the shell in `UnreadMessages`, whose `useUnreadMessages` follows the stream: `message:unread` replaces the count (until the next loader result, which is newer), and `message:new` reloads the inbox when the visitor is in it. The sidebar shows the count as a `Badge` on the bell (`navSections(locale, viewer, unread)`).
- The language of a page is the language the API answers in. `apiMiddleware` gives the API session the `:lang` of the request, which overrides the forwarded `shionlib_locale` cookie and has the browser store it, so requests without a `:lang` (fetchers to `resources.*`, the event stream) follow the page the visitor last opened, and `/` leads there next time.
- Uploading has one entry and one place to follow it. The upload page (`/:lang/upload`, `features/resource`) and the add-files and replace-file dialogs only collect what to upload and hand it to the upload manager; the form then navigates to the uploads page filtered to what is uploading (`sitePaths().uploading`, which a test keeps equal to the page's own URL scheme), showing its button as busy until the page changes, and the dialogs show a toast whose action goes there. Nothing else shows progress: the header's `UploadIndicator` is a link to the same place with a status dot.
- The uploads page (`/:lang/user/uploads`, `features/uploader`, the sidebar's 「我的上传」) is one list of what the caller uploaded, and one dimension describes every entry: its stage, in the order things happen, 上传中, 处理中, 已发布. Nothing on the page names a second concept for the same thing: no panel for transfers, no panel for resources, no table, no drawer. The `PageHeader` carries the title and the only 「上传资源」 button. The list is a `DataList` (`manual`, `pagination`, custom items through `children`). Its `renderHeader` holds three selectable `Chip`s with counts, one per stage and in that order, of which at most one is selected (selecting the selected one clears it, and without a selection the list shows every stage), then the search by game or file name and the order (`Select`, hidden for 上传中); everything is kept in the URL (`?status=&q=&sort=&order=&page=`; `useListing` debounces the search and keeps the scroll position for everything but a page change; a page past the end redirects to the last). What is uploading comes from this browser (`useUploads()`), so `entriesOf` puts those entries first on the first page of the unfiltered list and of 上传中, narrowed by the same search; the two other stages come from the API (`scope`). An entry therefore stays in the list as it moves on: its transfer ends, the server lists it as 处理中, later as 已发布. `useTransfers` keeps a submitted transfer on screen until the loader data that follows it arrives, so the transfer's entry and the resource's entry swap in one render and nothing below them jumps. The storage meter (`StorageMeter`), the tier (a `Tag` whose question mark shows the file limit in a `Tooltip`, as `FileState` does), the `Alert` of a frozen tier and four totals as `Statistic`s in a two-column grid (downloads, resources created within the API's recent window, games, files; the resource counts are already on the chips) sit in an `aside` `Card` beside the list from `xl` (sticky) and under it below. Submissions that reached the server are dismissed from the queue as soon as the page sees them; while anything is processing the page revalidates every 15 seconds (`useLiveRefresh`).
- This is a place to manage, so nothing in it may move while it is used, and it must still read as a list, not as a table: an attempt at fixed columns for size, state and controls was rejected as ugly. Every entry has the same anatomy (`ui/entry-shell.tsx`), whatever its stage, and leads with its files, not with the game. A file is one line (`ui/file-line.tsx`): the archive icon, the full name at body size in medium weight, the size, and then the file's state in a slot of fixed width, with a 4 px strip under the line that holds the upload's `Progress` and stays empty otherwise, so a line is as tall while it uploads as afterwards. At the top right sit the entry's stage as a `Tag` (`StageTag`: 上传中, 处理中, 已发布, the same three words as the chips) and, right beside it with no empty slot between them, its controls: one `⋯` for a resource, two for an upload. An entry with one control keeps the width of the second free at the end of its file column (`controlSlots`), so names wrap the same in every stage. One muted line under the files carries the facts: the game, the platform, language and engine tags, and where they apply the download count and the update time, or, for an upload, the game it is for (when it adds to or replaces something, a sentence naming the file instead: 「添加到 … 所在的资源」, 「替换 …」; never a bare kind tag, which was not understood) and the pace of the upload. What makes things move is avoided by construction: no control follows a text of variable width (a file line carries no control at all); a number that changes has a fixed width (`UploadTag` shows the percentage centred in `min-w-[4ch]`); pause or resume and cancel act on the whole submission from two fixed slots (`TransferControls`), and the first slot is never left empty while something can go on (pause, resume, or resume by choosing the files again); a file's own actions are in the entry's one `⋯` menu, flat for a single file and as a `DropdownMenuSub` per file for several (`ResourceMenu files`); a file that must be chosen again after a reload shows a small button in its state slot that opens a `Dialog` with the `FileUpload`, never a block above the list. Files that another browser or device is uploading are one entry of their own whose line under the files says so and when they can be taken over; each shows its percentage as of the last sync with the reason in a tooltip, and the entry has no controls at all (`lockedElsewhere`, `controlSlots={0}`), as has a submission of this browser while one of its files is held elsewhere. `ResourceFileLine` puts `FileState` in the state slot when a file is not clean (检查中, 保存中, 等待复核, 未通过检查). The game is a link to the resource on its game page, without a cover. Check a change here by measuring: run a slow upload and compare the bounding boxes of rows, bars, buttons and entries over time and across the hand-over, at desktop and phone width; none may change. The uploads page offers no download. On the game page a resource is a `ResourceCard`.
- Lists of names (developers, aliases, staff) go through use-intl's `format.list(...)`, which joins them the way each language does (「A、B 和 C」); `format.list` also accepts links. A list that may be long is truncated to one line with the full list in a tooltip, not cut with 「等 N 个」.
- A single string slot (an option's `description`) carries one fact, not several joined together.
- An entry with a picture in a list of choices (search dialog, game picker) renders `PictureOption` from `features/search`: a `w-9` frame on `bg-inset` (games: cover at 3:4; characters: portrait at 3:4 anchored to the top; developers: square logo, contained), the name, and one detail line (developers, the game, the number of works). Without a picture, the frame shows the kind's icon through `Image`'s `empty` slot. Commands (recent, trending, suggested terms, see all) keep an icon and a label.
- The search dialog is a `Dialog` (`placement="top"`, `renderBody`) holding a `SearchInput` and a `Listbox` whose options are rendered with `renderOption`. `CommandPalette` is not used because its items cannot be rendered by the caller. Enter in the input opens the full results page, the down arrow moves into the list, and picking a recent, trending or suggested term fills the input and returns focus to it. The panel adds no padding of its own (spacing comes from `SearchInput` and `Listbox`) and no navigation links, which the sidebar already has. Recent searches are plain options at the top of the list under a heading row the panel renders itself, because a `Listbox` group label is text only: the heading on the left in the group label's type (`size="xs"`, muted, medium) and a `Button variant="link" tone="danger"` with a trash icon on the right that clears them, at the same text size (`text-xs`). The row is inset by `px-3.5` on both sides, which is where an option's content starts and ends, so the heading lines up with the other group labels and the button with the options' right edge. To keep that row scrolling with the list, the `Listbox` gets `maxHeight="none"` and both sit in one `ScrollArea`.

## Catalog attribution

Resource notes, file history reasons and catalog intros (VNDB descriptions) are BBCode. `parseBBCode` (`~/shared/markup/bbcode`) turns them into nodes: `b`, `i`, `u`, `s`, `quote`, `spoiler` and `mask`, and `url` with or without a value; `size` and `color` keep only their text, and unknown or unbalanced tags stay as text. A link must be an `http(s)` address or a VNDB entry path (`/c123`, resolved by `vndbUrl` from `~/shared/catalog/vndb`); anything else keeps its label as plain text. `BBCodeText` renders the nodes with hina-ui only (`Text as="strong"/"em"/"u"/"s"` carrying the surrounding tone and weight, `Link underline` opening in a new tab with `rel="noopener noreferrer nofollow ugc"`, `Blockquote`, `Spoiler`), keeps line breaks (`whitespace-pre-line`), and takes `size`, `tone` and `className` so it can stand in for the `Text` it replaces; a clamped summary adds `whitespace-normal`. Meta descriptions use `bbcodePlainText`, which drops spoiler content.

BBCode is written in `BBCodeEditor` (`~/shared/ui/bbcode-editor`), placed inside the field's `FormField` like any input: a bare `Toolbar` (`size="sm"`) with icon `ToolbarButton`s for bold, italic, strikethrough, link, quote and spoiler (no underline: notes do not need it and it reads as a link) and, at the end, a `ToolbarToggleItem` 「预览」 with an eye icon whose text is visually hidden below `sm`; the field itself is the hina `Textarea`. A tool wraps the selection in its tag, or removes the tag when the selection is already wrapped, and keeps the selection (`applyBBCodeTool`, `~/shared/markup/bbcode-edit`); a link wraps a selected address as `[url]…[/url]` and otherwise leaves the cursor at the address of `[url=]…[/url]`. Preview swaps the textarea for a `Card` with the textarea's exact box (`rounded-md`, the measured height) and text position (padding from `--hn-control-px-md` and `--hn-control-h-md`), rendering `BBCodeText`, so switching moves nothing. Never put a `SegmentedControl` or `Toggle` next to the input inside a `FormField`: they claim the field's label and error state; the toolbar's toggle group does not.

A short fixed list where several values may be chosen (resource platforms with `PlatformIcon`, languages) is a row of `Chip selectable` in a `role="group"` with an `aria-label` (`ChoiceChips`, `~/shared/ui/choice-chips`): every option is visible and one tap toggles it. Not `CheckboxGroup` (a questionnaire look) and not `MultiSelect` (hides a handful of options behind a dropdown).

Text cut with `truncate` shows its full value in a `Tooltip` only when it actually overflows: `useOverflowing()` (`~/shared/ui/use-overflowing`, a `ResizeObserver`) gives the ref and the flag, the `Tooltip` is `disabled={!overflowing}` and the trigger gets `tabIndex={0}` only then. The trigger is sized to its text (`w-fit` with a `max-w-*`), otherwise the tooltip centres on an empty full-width box.

Game, character and developer data comes from Hikarinagi's open API, whose terms require naming Hikarinagi as the source and linking to the entry. Every page that shows such an entry renders `CatalogAttribution` (`~/shared/ui/catalog-attribution`) with the entity and its `h_id`: the text 「条目数据来自」 followed by Hikarinagi's wordmark (`app/shared/ui/hikarinagi-wordmark.svg`, inline, colours untouched) linking to `HIKARINAGI_SITE_URL/<galgames|producers|characters>/<id>`. Entry and editor URLs come from `~/shared/catalog/hikarinagi`. The tab that shows the catalog data (the game's info tab) ends with `CatalogCorrection` (「资料有误或不全？去 Hikarinagi 编辑」), linking to the entry's editor; corrections are not offered from menus. The Hikarinagi ID button keeps using `public/brand/hikarinagi-icon.webp`.

## Messages and locales

- Locales: `zh` (default), `en`, `ja`; URLs are `/<locale>/...`; `/` redirects by the `shionlib_locale` cookie, then `Accept-Language`, then `zh`.
- Each feature owns `messages/{zh,en,ja}.json`, registered under the feature name in `app/messages/{zh,en,ja}.ts`. `zh` defines the `Messages` type; `en` and `ja` must match it.
- Messages use ICU syntax (`{count, plural, ...}`, `{date, date, long}`) and are read with `useTranslations('<feature>')`; keys are checked at compile time.
- Dates are formatted in `Asia/Shanghai` on both server and client so hydration matches.
- Text from the API (titles, `failure.message`) is already localized or multilingual; pick game titles with `gameTitle(game, locale)`.

## Pages

- Every page route exports `meta` with a title (`<page> | Shionlib`) built from loader data; pages that can 404 return `[]` when `loaderData` is undefined.
- Error pages are `ErrorPage` (localized 401/403/404/5xx; a 5xx offers a retry). Under the text it shows what identifies the failure: status, error code, request ID with a copy button, and the stack of a thrown error (`ErrorDetails`). A page that cannot be loaded shows it inside the site, through the `ErrorBoundary` of the `routes/pages.tsx` layout, so the sidebar, the header and running uploads stay. `lang.tsx` keeps a boundary for when the site layout itself cannot load, and the root a minimal one for invalid locales.
- Links between pages are `<Link to={`/${locale}/...`} prefetch="intent">`.
- Entry detail pages (game; later character and developer) let the artwork carry the page. The header starts with a key visual: the first screenshot that is safe to show large (`bannerIndex`), as a wide rounded banner that opens all screenshots in a `Lightbox` (`useGallery`, never `Image preview`, since the cover overlaps it). The cover (with `preview`) overlaps the banner's lower edge (negative top margin, `ring-4 ring-canvas`), and beside it come the byline (developer · release date), the title and original title, aliases, platform and type `Tag`s, and one action row (download is the only solid, accented button; upload is outline neutral, and becomes the solid one when there is nothing to download; favorite is an outline neutral `IconButton` with a bookmark, filled once the game is in a list, because favorites are lists and not likes, so no heart and no accent colour; `CatalogAttribution` at the end). The external ratings (`GameScores`) sit beside the title block from `sm` and under it below: one block per source the game is linked to (`scoreSites`), headed by the site's own logo (Bangumi's `public/brand/bangumi-logo.png` in its colours; VNDB's wordmark `vndb-logo.svg` inline in `currentColor`, since its navy would vanish in dark mode, each with an explicit width from its aspect ratio so it starts at the same left edge as the lines under it; an SVG with `w-auto` stretches across the column and centres its art), then the score with one decimal and the vote count, or a dash and 「暂无评分」; the whole block links to the entry on that site, and since it is a link and not a card it gets only `hn-state-layer` (hover and press tint, `rounded-lg`, `p-2` offset by `-m-2` so the edges stay aligned), no `Ripple` and no press scale. `Statistic` is not used here because its `label` is text only. There is no `⋯` menu: every action in it duplicated something already on the page (the address bar, the attribution link, the score links). Without a usable screenshot the same grid renders without the banner, the overlap and the text column's top padding, so the title lines up with the cover. The tabs follow below; long-form text (the intro) lives in a tab and in the `description` meta.
- The resources tab keeps the PRD prototype's information order and drops what does not earn its space: the platform filter (`SegmentedControl`) appears only for more than three resources and there is no page-level download method switch (each `DownloadButton` menu already offers browser, aria2 and copy; the default lives in settings). Each resource is a `Card` (`padded={false}`, `p-4`, `gap="sm"`): `PlatformTag`s and outline language and engine `Tag`s, all `size="md"` with `h-7 px-2.5`, on the left, uploader, update time and download count (icon + text) on the right with a `⋯` `DropdownMenu` for history, report, edit and delete (below `sm` the facts move to their own row); the note through `BBCodeText`; files in a `Table` (`variant="secondary"`, header for screen readers only) with name (an archive icon, then the full name wrapping across lines, never truncated: it is what tells versions apart, and a hover tooltip does not exist on touch screens), size, checksum and the download button; below `sm` the checksum is hidden and the size moves under the name, leaving the name the width it needs. A file's scan state shows only when it is not clean, as a tag after the name that wraps under it on narrow screens.
- A page split into tabs (the game page: `/:lang/game/:id`, `/info`, `/characters`) is a parent route with one child route per tab. The parent loader loads everything the tabs share, so switching tabs never reloads the header; child routes have no loader of their own when the parent already holds their data and read it from the typed `matches` prop (`const [, , site, , game] = matches`: root, lang, site, pages, game). The tab strip is hina-ui `Tabs` with `value` taken from the URL and `onValueChange` navigating with `state: keepScroll` (`~/features/shell`), which tells the main scroll restorer to keep the position; a `hash` on such a navigation scrolls to that element (`#resource-12`).
- Slow, optional data (external ratings) is returned from the loader as an unawaited promise that never rejects at all: the use-case settles every request (`Promise.allSettled`) and drops what failed, because a promise that rejects before React Router attaches to it is an unhandled rejection that takes the server process down. It renders through `<Suspense>`/`<Await>`, and the fallback must take exactly the space of the result (no layout shift): render the same slots the result will fill, known from the synchronous data (which sources a game is linked to), with values that occupy the same line (a dash) and `Skeleton` wrapping the lines that will appear. (`Statistic loading` would not do: its skeleton is shorter than the number's line.)
