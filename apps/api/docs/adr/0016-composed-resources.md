# ADR 0016: A translated edition is composed on the server as a resource of its own

## Context
Most downloads of a translated game are an archive somebody made by hand: download the original, unpack it, copy a fan translation over it, pack it again and upload several gigabytes. The site already stores the original, and the patch is a few megabytes. When the translators publish a fix, the whole edition is made and uploaded again. A patch replaces files of the game, so the result must never take the place of what it was made from: the original has its own downloads, checks and history.

## Decision
The capability `internal/composition` composes a stored resource and an uploaded patch into a new resource.

- **A composition always yields a resource of its own.** The base and its files are read and never written: the run fetches the base from the bucket into its own directory and works on that copy. Nothing in `composition` can change a file row of the base.
- **What can be a base** is decided from what is already known (`BaseOf`): a published resource of the same game whose form is `portable`, whose main file (or set of volumes) is stored and passed its check, whose inspection (ADR 0014) lists its contents, and whose unpacked size is within `composition.max_unpacked_size`. Disc images, installers, resources without a form, files not read yet and resources that were composed themselves are listed with the reason. Any signed-in uploader composes onto any usable base.
- **A draft lives on the server** (`resource_compositions`, state `draft`). The patch and the optional saved games are ordinary finished uploads handed over with `upload.Service.Take`, which moves the file out of the spool into `<spool>/.compose/<id>/inputs/<role>/` and retires the session, so they count as neither a resource file nor an orphan. A job (`composition_read_input`) examines each input with the steps of an upload check (`scan.LocalService`: test, listing, nested archives, scan) without recording an inspection, and refuses what is encrypted, broken, not an archive, harmful or has too many entries. A patch whose SHA-256 equals an entry of 鲲 Galgame 补丁 carries the group, version and page of that entry as a suggestion; an outage of the other site means no suggestion.
- **The plan is drawn before anything is unpacked** (`Draw`), from the stored listing of the base and the listing of the patch: which folder of the base is the game and which folder of the patch holds the files to lay over it. Both are guessed by letting every patch file whose name also exists in the base vote for the pair of folders that would make them meet, and the uploader may choose others. Names are compared without case and in NFC, as Windows would. The plan counts and lists what is added and replaced, and names the conflicts (a file where the base has a folder, or below a file); a plan with a conflict or with nothing to apply cannot start.
- **Starting creates the resource**, unpublished, with the information the uploader gave (`download.ComposedService.Begin`), and queues `composition_run` on the queue `composition`. River may run four at once; the setting `composition.concurrency` (1 by default) is read when a job claims its slot, under an advisory lock, and a job without a slot is snoozed, so the setting applies at once. `composition.queue_limit` bounds how many wait.
- **The run has six steps**, each recorded with its times: `fetch` (the base from the bucket), `unpack` (base, patch and saves with 7-Zip, then a sweep that removes links, restores names written in a legacy code page and clears permissions), `apply` (the overlay is computed in Go from the two trees and done with renames, never by unpacking one archive over another), `pack`, `check` and `store`. The result is one 7z archive, LZMA2, not solid, with up to three folders at its root: the game under the base's own wrapping folder (or the game's title), `全CG存档` and `汉化补丁` (the patch archive as it was uploaded, when the uploader keeps it).
- **The result is checked like an upload** (the same test, listing, scan and previews, recorded as its inspection) and only then stored and published in one transaction with the event `composed`, whose changes name the base. A harmful or broken result fails the composition and publishes nothing.
- **A new patch rebuilds from the base, not from the last result** (`Rebuild`): a second composition with `target_file_id` takes the new patch, inherits the saves by hard link and starts itself once the patch is read. The new object is put first and the file row is switched to it in place (`ReplaceStoredContent`, event `recomposed`, favourites are told as for a re-upload), so the earlier file is served until the switch and the resource keeps its id, comments and download count. The earlier object is purged afterwards.
- **Failures are told apart.** What will not go away by itself (the base is gone, an archive cannot be unpacked, a chosen folder is missing, no room, a harmful result, the queue or the quota is full) fails the composition with a reason the uploader reads and may retry; anything else is returned to River and tried again, and the last attempt fails the composition as `internal`. The uploader gets a message when a composition finishes or fails.
- **Room is admitted twice**: the estimated size of the result against the uploader's quota when the composition starts, and the working space (`Needed`: the base packed and unpacked, the patch and saves unpacked, the result) against the free space of the spool when the run begins.
- A task (`composition_clean`, every ten minutes) discards drafts nobody touched for `composition.draft_ttl`, removes directories without a row and queues again any work whose job was lost.

## Alternatives
Replacing the files of the base with the patched ones: rejected by the product owner, a patch overwrites game files and the original must stay what it is. Applying the patch in the browser or handing out a script: the visitor still downloads and repacks gigabytes, which is the work this removes. Storing the patch and applying it at download time: every download would cost a composition. Unpacking the patch over the base with 7-Zip: the tool decides case, encoding and conflicts silently; computing the overlay first is what lets the uploader see the plan and lets a conflict stop the run. Fetching patches from 鲲 Galgame 补丁: the other site only gives page addresses.

## Consequences
The worker needs disk for one composition at a time by default: about the base twice (packed and unpacked) plus the result, on the upload spool. Saved games stay on the spool for as long as their resource exists, so a later patch can be composed without uploading them again. A base without an inspection cannot be composed on until `shionlib-api inspect` has read it. Installers, disc images, patches that are installers or binary diffs, and encrypted archives are out of scope.
