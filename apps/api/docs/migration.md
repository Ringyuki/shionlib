# Migrating from the NestJS backend

## Strategy

1. The Go backend serves the same HTTP contract (paths, envelope, business codes, cookies) so the existing web client and its Playwright suite can run against it, and the new client is built on the same contract through OpenAPI.
2. It runs against the same PostgreSQL database. `shionlib-api migrate up` adopts a Prisma-managed database (marks `20260925074133_baseline` applied when `_prisma_migrations` shows the final Prisma migration) and then applies forward migrations.
3. Modules are ported one capability at a time with tests that pin legacy-visible behavior (see `.claude/skills/go-backend/recipes/migrate-module.md`).

## Per-module compatibility checklist

HTTP method/path · request schema · response schema · status code · business code · authentication · authorization · side effects · DB writes · transaction behavior · events/jobs · cache behavior · timeouts · retries · idempotency.

## Intentional deviations

| Area | Legacy behavior | New behavior | Reason |
|---|---|---|---|
| Path/query parsing | non-integer path id → 400 `code:400` | 422 `COMMON_VALIDATION_FAILED` with field details | one validation pipeline |
| Unknown query parameters | rejected with 422 | ignored | caches and proxies append parameters |
| Optional auth | ignored the family block; `Bearer undefined` shadowed the cookie | blocked families and invalid tokens are treated as stale guests; placeholder bearer values fall back to the cookie | security, consistency with required auth |
| `GET /favorites` as guest without `user_id` | listed every user's lists, including private ones | empty list | data leak |
| `PATCH /favorites/:id` without `name` | could fail with `FAVORITE_NAME_ALREADY_EXISTS` | name check only when a name is sent | bug |
| `DELETE /favorites/:id/games/:game_id` | revealed item existence to non-owners | ownership checked first | data leak |
| Concurrent duplicate inserts | unique violations surfaced as 500 | mapped to the business conflict code | correctness |
| Default locale | `en` | `zh` | product direction |
| Realtime notifications | socket.io namespace `/ws`, client emits `message:unread:pull` | Server-Sent Events at `GET /message/stream` (events `message:new`, `message:unread`, `ping`); the unread count is sent on connect | plain HTTP, no socket.io dependency (ADR 0007) |
| Message texts | `title`, `content` and `link_text` were translation keys (`Messages.System.…`) that the client translated with the free-form `meta`; `message:new` carried the key as `title` | the API writes them in the caller's language from `internal/platform/i18n/locales/*/Messages.json`: codes in `meta` become words (report reasons, severity, check results), times are given in UTC+8, sentences about absent values are left out; text that is not a key is returned as stored. List items carry an `excerpt`. `message:new` carries `id`, `type`, `tone` and `created` only, and the stream with both event shapes is in the OpenAPI document | a client cannot type `meta`, and a key is not something to show |
| Message push timing | `message:new` emitted before the transaction committed | emitted after commit | phantom notifications on rollback |
| `POST /message/:id/read` for a missing or foreign message | 500 | 404 `MESSAGE_NOT_FOUND` | bug |
| Catalog data | read at request time from Hikarinagi internal APIs | materialized locally from catalog sources (see ADR 0006) | removes internal coupling |
| Partner API (`/partner/*`) | secret-authenticated download data for Hikarinagi | removed | internal communication removed |
| Configuration | `*_MS`/`*_SEC` numbers, `REFRESH_TOKEN_ALOGRITHM_VERSION` | Go durations (`60s`, `1h`), corrected names; see `.env.example` | clarity, validation at startup |
| Games deleted at the source | the shell stayed visible and its detail routes returned 404 | the game is hidden (`status = 2`) when the source reports it gone; merged entries are marked missing and the merge target is imported | consistent lists and details |
| Admin panel support | the panel counted and listed through the content endpoints alone; stalled checks were handled from the command line; site figures had no resources, no daily comments and estimated trends | `GET /admin/pending` (what waits: reports, malware cases, stalled files, comments, walkthroughs; and `ai_alerts`, the scenes without a usable model plus the suspended routes of enabled providers, for the mark on the AI gateway); `GET /admin/stats/storage` (spool use and reserve, files uploading, awaiting check and store, stored total); the overview adds resources, comments, downloads and views of today; trends carry real daily downloads and views, counted in `site_daily_stats` from the day it is deployed; `GET /admin/content/stalled-checks` with `POST …/{file_id}/recheck` and `DELETE …/{file_id}`; `GET /admin/content/download-resource-report-policy` and `GET /admin/content/malware-scan-policy` (what a verdict does, read from the settings); a report's detail carries `reporter_record`; `GET /admin/content/malware-scan-cases?reviewed=true` lists only decided cases; an admin user's detail carries `violations`; the walkthrough moderation list takes and shows `held`; `GET /admin/upload-tiers` lists what each upload tier takes and allows; `GET /admin/users/{id}/sessions?live=true` lists only the sessions that can still be used; the user list sorted by last login puts those who never signed in last, in either direction | the rewritten panel shows the consequences of a decision before it is taken and never restates a setting as a number of its own |
| Third-party credentials | `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`, `BANGUMI_CLIENT_ID` and `BANGUMI_CLIENT_SECRET` were read from the environment at startup | the same four are also settings (`oidc.*`, `bangumi.*`; the secrets of kind `secret`, which the API never returns); a value set in the admin panel wins and applies to the next request, an unset one falls back to its variable | replacing a credential needs no redeploy |
| Catalog administration | none | `GET /admin/catalog/sources` (each source with the games, developers and characters it provides here, its position in the change feed, the outcome of the last pull and `refresh_seconds`, the age after which its entries are fetched again), `POST /admin/catalog/sources/{source}/sync` (pull the changes now), `GET /admin/catalog/search` (each hit says whether it is here, `local_id`, or kept out, `excluded`; a number the search does not list leads the first page as a hit without a title, so an entry can be imported by its number), `POST /admin/catalog/import` (synchronous; also brings back an excluded entry, which stays excluded when the import fails), `POST /admin/catalog/import/queue`, `GET /admin/catalog/excluded` (the entries kept out of imports, with the name they had and who removed them) | operators can see the state of the sync, run it, import or refresh one entry and bring back one they removed |
| `DELETE /character/:id` | no guard; any guest could delete a character | requires ADMIN (401 `AUTH_UNAUTHORIZED`, plain 403 below admin), like `DELETE /developer/:id` | security hole |
| Character and developer ids | `GET /character/:id`, `GET /developer/:id`, `/developer/list` and the credits inside game payloads used Hikarinagi ids; `h_id` echoed the path id | every id is the local `game_characters.id` / `game_developers.id` (`/game/list?developer_id=&character_id=` too); `h_id` is the stored source id or `null` | catalog is local (ADR 0006) |
| Game route caches | `/game/list`, `/game/recent-update`, `/game/:id`, `/header`, `/details`, `/characters` cached 30 min per user and content limit | read from local tables on every request; only the Bangumi/VNDB scores (7 days) and sitemaps (1 hour) are cached | local reads are cheap; no stale views or visibility after edits |
| Game detail payloads | `link[].id` was index+1, `relations_from[].id` the Hikarinagi target id, `relation` the raw upstream string, `tags[].tag_alias` always `null`, character `age` a string | `link[].id` = `game_links.id`, `relations_from[].id` = `game_relations.id`, `relation` = `game_relation_type` value, `tag_alias` from `game_tag_relations`, `age` an integer; developers are the `开发` credits | data comes from local tables |
| `POST /game/:id/view` for a missing game | 500 (Prisma P2025) | 404 `GAME_NOT_FOUND` | bug |
| `GET /game/score/vndb/:id` without a VNDB result | `data` key omitted | `data: null`, nothing cached | consistent envelope |
| `GET /game/list` array filters | qs accepted `filter[tags][]=a`, `filter[tags][0]=a` and scalars | only the bracket form `filter[x][]=` the web client sends; dates accept RFC 3339 or `YYYY-MM-DD` | Huma query binding |
| `GET /search/games` | engine-specific item shapes (pg, Meilisearch or Hikarinagi); the `pg` engine searched hidden games, ignored the resource setting and matched intros, characters and staffs; every search was recorded for the trends | replaced by `GET /search?q=&types=game&types=developer&types=character&page=&pageSize=`: the catalog source finds the entries (ADR 0006), upstream ids map to local rows, unknown entries are skipped and queued for import; one section per kind with the source's total; games use the `/game/list` item shape, hide `status != 1` and rated games for strict viewers, and follow the resource setting as the legacy engines did (guests and users who keep it on get only games with resources, kept from the source's first 100 hits; `resources=any` lifts it and `resources=required` applies it whatever the setting); developers and characters appear only when linked to a visible game; no highlights; the `tag` filter lives on `/game/list?filter[tags][]=`; searching records nothing | one search behaviour without a local engine to keep in sync |
| Search analytics | separate unprefixed Redis client (`trends:*`, `sugg:prefix:*`) that refused to boot with `REDIS_DB=0`; any query length recorded, prefixes split UTF-16 units; suggestions were past queries sharing the prefix | trends live under the client prefix (`<prefix>:search:trends:<window>`) and count only keywords sent to `POST /search/record`, up to 64 characters; the River job is not retried; `GET /search/suggest` returns a plain array of titles and aliases of visible games that start with the prefix, hottest first | bounded memory, suggestions that lead to a game |
| `GET /search/tags` | `limit` unbounded; names matched case-sensitively, aliases only exactly | moved to `GET /tags`; `limit` 0..100; case-insensitive substring on names and aliases, `display_name` rules unchanged | validation, consistency |
| `GET /character/list` `q` | names were ANDed together, so only the alias ILIKE matched; no order | name (jp/zh/en) or alias case-insensitive substring; ordered by id | bug |
| `GET /comment/game/:game_id` | every comment of the game in one flat list, oldest first; a reply could land on another page than the comment it answers; items had no editor state | pages of threads: the items are the root comments, `order=newest` (default) or `oldest`, each with `replies` (the visible comments of its thread, oldest first: replies, replies to replies, and replies whose parent was deleted); `meta.totalItems` counts threads and `meta.comments` every visible comment; items, `/user/datas/:id/comments` and the `comment` of a message carry `content`, the editor state | the page shows a comment with its answers, and renders the state itself |
| Comment and walkthrough content | Lexical editor state (`{"root": …}`) in `content` and the HTML rendered from it in `html` | a rich text document (`{"type":"doc","content":[…]}`, ADR 0013) in `content` and its plain text in `text`; every payload that carried `html` carries `text`; the OpenAPI contract describes the document (`RichTextDocument`); a comment takes paragraphs with bold, links and spoilers, and so does the note of a walkthrough; that is the whole vocabulary | one editor on the client that stores a document with a schema; nothing renders HTML from the API |
| `GET /activity/list` | a log of everything recorded: every stage of an upload (received, checked, stored, check failures), entry creation and edits, comments and walkthroughs, whatever became of them; `category` in comments/gameCreates/walkthroughCreates/edits/files | what became public and still is: a file stored for a published resource (`FILE_UPLOAD_TO_S3`), an accepted comment (`COMMENT`), a published walkthrough (`WALKTHROUGH_CREATE`), each only while the file, comment or walkthrough and its game are visible to the viewer; `category` in files/comments/walkthroughCreates; `type` is an enum; `file` is `{id, resource_id, file_name, file_size}` or `null`; `developer` and `character` are gone | the page shows what happened on the site, not the upload pipeline; entries are created by the catalog sync now, so nothing records creations and edits any more; failed checks and files under review were public |
| Walkthroughs | an article: a title and a rich text, any number per author and game; `POST /walkthrough`, `PATCH /walkthrough/:id`, a paged `GET /walkthrough/game/:id` of titles and excerpts, `GET /walkthrough/:id?withContent=` | what a player follows: an optional `note` (a comment-like document) and `routes` in the order they are best played, each with a `key`, a name, the ids of the game's characters it is about, the keys of the routes to finish first (`requires`), another `condition`, an `ending` and `steps` of five kinds (`choice` with `text` and `remark`, `save` and `load` with `slot`, `note` with `text`, `gap`); no title, no excerpt. An author has one walkthrough per game: `PUT /walkthrough/game/:id/mine` creates it or replaces what they wrote (`status` `DRAFT` or `PUBLISHED`; publication needs a note or a route and a name and a step in every route, `WALKTHROUGH_EMPTY` 560104 and `WALKTHROUGH_ROUTE_INCOMPLETE` 560105; a second row for the same author and game is `WALKTHROUGH_ALREADY_WRITTEN` 560106). `GET /walkthrough/game/:id` answers an array, not a page: the caller's own walkthrough first, published or not, then the published ones by latest update (at most 50), each with `route_count`. `GET /walkthrough/:id` always carries the note and the routes, with `game_id` and `review_pending`. `GET /user/datas/:id/walkthroughs` lists `route_count` and the game, the owner's unpublished ones first; neither list takes `status`. The activity feed's `walkthrough` is `{id}`; the admin list sorts by id, created, updated or status, and its detail carries `note` and `routes` | a walkthrough is read step by step on the game page, not as an article (PRD prototype of 2026-10-11) |
| `GET /comment/game/:id` | pages only by number, so a link to one comment could not open the page it is on | `focus=<comment id>` answers the page that holds the thread of that comment (`meta.currentPage` says which); a comment the viewer cannot see, or of another game, leaves the requested page | a message or a profile leads to the comment itself |
| `GET /user/:id` | `resource_count`, `favorite_count`, `comment_count` and `walkthrough_count` counted every row of the user: removed and unpublished uploads, the games in private lists, deleted walkthroughs and blocked comments included | they count what the profile of the same viewer shows: published uploads, the games in public lists, visible comments and published walkthroughs; for the user themself their unpublished uploads, drafts and hidden walkthroughs as well, but never their private lists, which a profile does not show even to its owner; and for a viewer who does not see rated games no upload, comment or walkthrough that belongs to one | a profile said "3" over a list of one |
| Profile pictures | an avatar and a cover, each only replaced by another upload | adds a page background: `POST /user/info/background` (form field `background`, up to 5 MB, stored at most 2560 wide under `user/<id>/background/`), `background` in `GET /user/me` and `GET /user/:id`; `DELETE /user/info/cover` and `DELETE /user/info/background` clear one picture; `POST /user/info/profile-backgrounds` stores `show_profile_backgrounds` (default `true`, in `GET /user/me`), whether the viewer wants the backgrounds of other users shown | profile redesign |

| `GET /developer/list` | Hikarinagi producer list, upstream `works_count` | local developers, the ones with the most visible games first, then by name and id; `works_count` counts visible games | catalog is local |
| `GET /bangumi/get` | open proxy to any `api.bgm.tv/v0/{path}/{id}/{type}` with the site token | `path` in subjects/characters/persons/episodes/indices, numeric `id`, `type` in subjects/characters/persons; anything else is 422 | abuse of the shared OAuth token |

## Redis

The family-block keys keep their legacy names (`<prefix>:auth:family:blocked:<fid>`), so sessions blocked before the cutover stay blocked. Every other cache entry is rebuilt; legacy cache keys can be flushed after cutover.

Catalog keys: the recent-update sorted set moves from the ioredis key `<prefix>game:recent_update` (no separator) to `<prefix>:game:recent_update`; copy it with `ZUNIONSTORE <prefix>:game:recent_update 1 <prefix>game:recent_update` at cutover or let admins re-mark games. Provision the Bangumi OAuth tokens with `SET <prefix>:bangumi:tokens "$(cat config/bangumi-tokens.json)"`, or authorize the site once from the admin panel's catalog page after setting the application's id and secret; without them the Bangumi score and proxy routes return 500 as before. Search trends and suggestions restart empty.

Short-lived auth state moves to new keys under `<prefix>:auth:` (`verification:<uuid>:<email>`, `password-reset:<token>:<email>`, `passkey:challenge:<flow>`, `refresh:replay:<session>`). Verification codes, reset links, passkey ceremonies and OIDC transactions started on the legacy backend in the last 30 minutes before the cutover must be restarted; refresh tokens, password hashes and passkeys are unaffected.
